# DEN FREEZE POLICY

## purpose
Define how freezing should work in the DEN-style, ability-first version of `SEAL_HAT_LLM`.

The central rule is:

**Freeze what is mature. Train what is missing, immature, or newly added.**

This policy keeps identity and governance stable while still allowing governed growth.

---

## core doctrine
The repository should not keep every part of the system permanently open just because dynamic growth is allowed.

A DEN-style system is healthiest when:
- mature constitutional behavior is protected
- new ability surfaces remain trainable while immature
- useful new structures are frozen once they mature
- reopening frozen structures is rare and evidence-backed

A dynamic system without freezing becomes drift.
A frozen system without growth becomes stagnation.
This policy defines the governed middle path.

---

## freeze levels

### 1. constitutional freeze
Protect the continuity-of-self surfaces.

Freeze once stable:
- language coherence
- slot awareness
- harness obedience
- governance refusal
- escalation discipline
- identity continuity

These are the most expensive abilities to damage and the least acceptable to let drift casually.

### 2. mature-module freeze
Freeze ability modules that have repeatedly proven useful and stable.

Examples:
- retrieval-planning overlays
- OCR or layout branches
- tool-routing overlays
- multimodal fusion branches
- verifier modules

### 3. specialist-core freeze
Freeze the stable core of a specialist once it reliably performs in-lane.

The lane identity and governance obedience of a mature specialist should not be casually reopened just because improvement is possible.

### 4. stage freeze
A module or branch may be trained while immature, then frozen once it reaches stable maturity.

This is the most developmentally natural pattern.

---

## freeze policy by structure

### constitutional root
Default policy:
- frozen after formation

Keep frozen:
- language foundation
- slot/harness behavior
- governance discipline
- identity continuity

Reopen only if:
- there is a constitutional-level defect
- repeated evals confirm the defect
- memory/routing/prompt fixes failed
- overlays/branches failed
- parent and harness approve the intervention

The constitutional root should be the last place reopened, not the first.

### parent
Default policy:
- stable base frozen
- control overlays trainable

Freeze:
- parent base backbone
- identity and governance core
- stable arbitration behavior once proven

Train:
- routing overlays
- confidence calibration layers
- growth-governance overlays
- specialist-selection logic

Reopen parent base only if:
- routing is repeatedly unsound
- arbitration is repeatedly failing
- governance interpretation is broken
- overlays clearly cannot fix it

Even then, reopen only the smallest necessary top slice.

### ability overlays and branches
Default policy:
- train while immature
- freeze once stable

Examples:
- modality branches
- verifier modules
- tool-use overlays
- retrieval overlays
- fusion branches

A useful DEN pattern is:
- observed ability gap
- growth experiment
- shadow evaluation
- activation
- freeze after repeated stability

### specialists
Default policy:
- specialist core frozen when mature
- lane-specific overlays remain the normal growth surface

Freeze:
- lane identity
- governance obedience
- stable tool discipline
- stable retrieval habits once proven

Train:
- lane adapters
- lane-specific expert modules
- modality-specific specialist extensions
- bounded integration layers

Reopen specialist base only if:
- the lane itself is structurally broken
- adapters cannot fix it
- repeated eval evidence justifies the risk

### micro-experts and helper branches
Default policy:
- short train/eval cycle
- freeze early if useful
- retire quickly if not worth it

These should be the least trusted and most replaceable structures in the system.
They should not remain permanently half-trained.

### router and gating logic
Default policy:
- more trainable than the constitutional core
- still versioned and eval-gated

Routing stays dynamic longer because a DEN-style system depends on:
- selecting the right module
- spending the right compute
- escalating at the right time

Even so, routing should be frozen at milestones and reopened only deliberately.

---

## freeze policy by developmental stage

### infancy
- almost everything trainable
- heavy supervision
- no trust

### childhood
- core begins freezing
- new overlays still trainable
- repeated skills form

### adolescence
- mature modules start freezing
- weak/new abilities stay open
- routing remains somewhat adaptive
- evals matter more

### adulthood
- constitutional core frozen
- mature overlays frozen
- mature specialist cores frozen
- only new ability-growth surfaces remain trainable

This matches the developmental philosophy of the repository.

---

## reopening rules
A frozen structure should reopen only if all of these are true:
1. repeated failure exists
2. evals confirm it
3. memory/routing/prompt fixes failed
4. overlays/adapters failed
5. the impact justifies the risk
6. parent and harness approve the intervention

Reopening is not casual maintenance.
It is a governed corrective action.

---

## practical freeze matrix

### constitutional root
- default: frozen
- preferred fix path: overlays, branches, descendants
- reopen threshold: highest

### parent
- default: frozen base, trainable control overlays
- reopen threshold: very high

### ability overlays
- default: train while immature, freeze when mature
- reopen threshold: medium

### specialists
- default: frozen mature core, trainable lane overlays
- reopen threshold: high

### micro-experts
- default: train briefly, freeze early or retire
- reopen threshold: low if cheap, but retirement preferred

### router/gating
- default: partially trainable longer than the rest
- reopen threshold: moderate, but always versioned and eval-gated

---

## anti-patterns
Do not:
- keep the whole system permanently open because “dynamic” sounds sophisticated
- reopen the constitutional root every time a specialist ability is weak
- leave micro-experts in endless half-trained limbo
- confuse routing drift with healthy growth
- treat freezing as failure instead of maturity
- treat bigger size as a substitute for stable ability

---

## summary
The DEN freeze doctrine for `SEAL_HAT_LLM` is:
- freeze what is mature
- train what is missing or newly added
- protect constitutional continuity first
- let specialists and overlays carry most growth
- freeze stable ability modules after they prove themselves
- reopen frozen structures only by evidence-backed parent+harness approval

The shortest version is:

**Freeze the self; train the growth surface.**
